# 登录与账号体系设计

## 目标与范围

第一阶段为 RTC Agent 增加项目自有的用户名/密码登录。认证服务和用户数据由本项目后端维护，使用独立 PostgreSQL 数据库；不调用网关的登录 API，也不访问网关数据库。

首版不做短信、邮箱验证码、第三方登录和复杂的组织/角色管理。登录身份与 RTC 房间身份是不同概念：用户账号 ID 稳定，RTC 的 room/user/token 按每次通话分配。后续创建 Agent 会话时，后端从登录 Cookie 解析稳定账号 ID，再关联会话与账号；不能把浏览器传来的 user_id 当成已认证身份。

## 后端已实现

- `POST /api/auth/register`：用户名密码注册；成功后直接建立登录会话。
- `POST /api/auth/login`：校验账号并建立登录会话。
- `GET /api/auth/me`：返回当前登录用户。
- `POST /api/auth/logout`：撤销数据库中的会话并清除浏览器 Cookie。
- 密码采用 Argon2 哈希；用户登录失败返回统一错误，未知用户也执行 dummy hash 校验。
- 浏览器持有随机 HttpOnly Cookie；数据库只保存其 SHA-256 摘要。登出可以立即撤销当前会话；默认有效期 12 小时，不提供刷新令牌或全端登出。
- 用户响应由 `/me` 提供稳定用户 ID、项目角色和权限。当前项目只有普通 `user` 角色，权限数据为空；Agent 会话接口额外按 `account_id` 做资源归属校验。
- 登录失败按用户名哈希 5 次/15 分钟、来源 IP 哈希 30 次/15 分钟限流，封锁 15 分钟；登录日志不记录密码、原始用户名、原始 IP、Cookie 或请求体。
- 新建数据表：`app_users`、`app_auth_sessions`、`app_login_attempts`。数据库由 SQLAlchemy Async 与 Alembic 管理。

## 登录页交互实现

建议在 RTC 主页面前增加独立登录页，保持现有 Arco UI 风格，布局简洁：

1. 页面中央卡片，标题“登录语音助手”，用户名、密码输入框和“登录”主按钮。
2. 次要操作“创建账号”切换注册表单；注册需确认密码并提示密码至少 8 位。
3. 登录成功后查询 `/api/auth/me`，进入原 RTC 场景页；刷新页面时先查询当前账号，已登录则直接进入。
4. 401 返回登录页；网络或服务错误在表单附近展示，不清空用户名；登录失败统一提示“用户名或密码错误”。
5. 右上角账号菜单展示用户名及“退出登录”。退出时调用接口撤销服务端 Cookie，再清除前端状态并返回登录页。
6. 登录表单不提供“记住我”：会话时长由服务端配置；Cookie 不可被 JavaScript 读取。

## 前端与 Agent 的接入边界

浏览器请求使用 `credentials: 'include'`。登录后前端再请求 `/api/auth/me`，仅按该服务端结果维护认证状态；Agent 会话创建接口依赖 Cookie。会话归属由服务端从 Cookie 得到，AgentSession 中保存稳定 `account_id`，另行保存 RTC `room_id`、RTC `user_id`。ASR 请求使用 RTC 身份时继续单独传给 ASR 适配器，不能复用账号 ID 代替 RTC UserId。

前端现已按上述设计实现登录/注册、刷新登录态恢复、路由保护、顶部用户名和退出登录；登录及登出请求携带 Cookie。登录后的 `/getScenes` 每次为浏览器请求生成独立 RTC 房间、RTC user_id 和短期 Token，因此不同用户及同一用户多端不会共用固定房间身份。Agent 会话创建要求登录，服务端从 Cookie 读取稳定账号 ID 写入进程内会话；ASR WebSocket、LLM 轮次、打断和关闭接口会校验会话所有者。RTC user_id 仍独立作为 RTC/ASR 身份使用。

## 配置与运行

数据库连接通过 `python_server/.env` 中的 `DATABASE_URL` 配置。真实 `.env` 已加入忽略规则；提交时只提交 `.env.example` 占位配置，不能把数据库密码放进版本库。

本地开发需要允许 Cookie 的明确来源，例如 `http://localhost:3000`，开发模式可将 `AUTH_COOKIE_SECURE=false`。`APP_ENV=production` 时默认启用 Secure Cookie；生产必须使用 HTTPS，并把 `CORS_ALLOW_ORIGINS` 改成实际前端域名。`AUTH_COOKIE_SAMESITE=none` 仅用于跨站前后端，并要求 Secure Cookie。登录 Cookie 的跨源写请求会校验 Origin。注册默认开启；封闭部署可设置 `AUTH_ALLOW_REGISTRATION=false`。

## 参考网关认证与数据管理

网关后端采用 FastAPI、SQLAlchemy Async 和 Alembic；`users` 使用 UUID 主键，`auth_sessions` 保存短期 JWT 的 `jti` 以支持撤销。密码采用 Argon2；角色 `admin/user` 属于网关管理域，不能复制到 RTC Agent。网关前端目前把 JWT 放在 `localStorage`；本项目选择 HttpOnly Cookie，减少脚本读取凭据的风险。两个应用共用 PostgreSQL 服务并不意味着共用用户表或权限。本项目数据库为空库，无需导入或兼容网关账号；未来 SSO 应通过 OIDC 的稳定 `sub` 映射本地账号。

当前没有密码重置、邮箱验证、第三方登录、业务管理员或项目成员权限需求。若以后增加，需要分别建立本项目的权限和资源关系，不继承网关管理员角色。

初始化/升级表结构：

```powershell
cd python_server
uv sync
uv run alembic upgrade head
uv run uvicorn app:app --host 0.0.0.0 --port 3001 --reload
```
